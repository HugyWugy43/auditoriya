# Аудит и обновление интерфейса — 5 октября 2026

## Вывод

В исходном проекте были функциональные ошибки и обходы прав доступа. После исправлений основные сценарии проверены на настоящих Java-сервисах и отдельной PostgreSQL 17: вход, чтение каталога, создание и отмена бронирования, редактирование пользователя, контроль пересечений и ролей. Полностью готовой к публичной эксплуатации систему считать пока нельзя: оставшиеся ограничения перечислены ниже.

## Сохранение архитектуры

Сохранены четыре отдельные приложения: API Gateway, User Service, Room Service, Booking Service. React обращается к Gateway; сервисы взаимодействуют через HTTP. Общая PostgreSQL и существующее разделение таблиц сохранены. Завершение бронирований выполняет планировщик Booking Service. Новый монолит, общий сервер React/backend или подмена API демонстрационными данными не добавлены.

Изменение схемы: в `bookings` добавлено числовое поле `version` для оптимистической блокировки. Текущий Hibernate `ddl-auto=update` добавляет его автоматически; для развёртывания на существующей рабочей базе нужна контролируемая миграция и резервная копия.

## Найдено и исправлено

| Проблема исходного кода | Исправление |
|---|---|
| Будущая бронь делала аудиторию занятой уже сейчас | Занятость определяется условием start ≤ now < end, отдельно показывается ближайшая бронь |
| Ошибка загрузки броней превращалась в пустой список и ложную доступность | Общая загрузка данных, явная ошибка и статус «неизвестно» |
| Браузеры самостоятельно завершали брони через PUT, создавая повторные запросы | Все такие записи удалены из клиента; сервер завершает просроченные записи каждые 30 секунд |
| Разрешалось нулевое время занятия | Проверяется строгое start < end |
| PUT менял время без проверки конфликтов | При изменении проверяются интервал, пересечения и активность аудитории |
| Два одновременных запроса могли занять один интервал | PostgreSQL advisory lock на аудиторию внутри транзакции; работает и между экземплярами Booking Service |
| Запоздалое редактирование могло перезаписать отмену | Оптимистическая версия записи; конфликт возвращает 409 |
| Неактивная аудитория могла бронироваться через API | Booking Service проверяет isActive у Room Service |
| Роли защищались главным образом скрытием кнопок | Каждый сервис проверяет JWT и права перед изменением данных; преподаватель работает со своими бронями, администратор управляет ресурсами |
| Отмена доверяла переданному userId | Автор действия извлекается из проверенного токена; подставить администратора через query нельзя |
| Можно было задать другого организатора от имени преподавателя | Для преподавателя userId определяется по токену; выбор другого организатора доступен администратору |
| API пользователей возвращал password; обновление профиля повторно хешировало уже полученный хеш | Поле password доступно только для входящих данных; обновление без пароля сохраняет существующий пароль |
| Ошибочный пароль вызывал перезагрузку страницы и скрывал сообщение | Ответ 401 на login остаётся в форме; сетевой сбой проверки сессии не удаляет токен |
| UI отправлял SEMINAR, а Java ожидала SEMINAR_ROOM | Типы согласованы, добавлено отображение STUDY_ROOM |
| Разработка обращалась к сервисам в обход Gateway | Vite использует единый прокси /api через Gateway |
| Docker Compose не запускал клиент | Добавлен контейнер клиента; сборка использует npm ci и lock-файл |
| Контейнер и браузер могли по-разному понимать местное время | Бизнес-время Booking Service и интерпретация временных меток клиентом закреплены за Москвой |

## Интерфейс

Референсы использованы как ориентир оформления: тёмная навигация, спокойные пастельные карточки, крупные числа, цветные интервалы расписания, личный план справа. Сделаны обзор, каталог, расписание, избранное, личный кабинет и новая форма бронирования. Сохранены административные разделы. Добавлены адаптивная компоновка, клавиатурный поиск, фокус в диалогах, обработка пустых состояний и ошибок, анимации с поддержкой уменьшения движения.

Избранное хранится в localStorage с ключом пользователя. Это список отслеживаемых помещений, а не серверная подписка: синхронизации между устройствами, email и push-уведомлений нет. Доступность обновляется опросом раз в 30 секунд; при сохранении сервер повторно проверяет интервал.

## Что проверено

- Production-сборка React/Vite завершилась успешно.
- Собраны все четыре Java-приложения.
- 10 тестов клиентской логики: будущая бронь, границы интервалов, отменённые и завершённые записи, неактивная аудитория, ближайшее занятие, пересечения, переход через полночь и дата кампуса.
- 9 тестов Booking Service: валидация, конфликты, порядок блокировки, запрет восстановления отменённой брони, чужая отмена, серверное завершение.
- 1 тест сериализации User: пароль принимается на входе, но не возвращается клиенту.
- 26 успешных сквозных API-проверок в завершившемся прогоне на PostgreSQL. В частности, из 10 одновременных запросов на один интервал ровно 1 получил 201 и 9 получили 400.
- Отдельно проверен реальный планировщик: просроченная CONFIRMED запись стала COMPLETED без изменения через клиент.
- В браузере проверены вход преподавателя, фильтр лабораторий, добавление в избранное и сохранение после перезагрузки, карточка помещения, переход к форме с выбранной аудиторией, создание занятия, отображение в «Только мои» и подтверждённая отмена из диалога.
- Проверено адаптивное отображение при ширине 390 px; горизонтального переполнения страницы нет; мобильное меню открывается и закрывается после перехода.

Стенд: отдельная база `audit_ui_test`, порт PostgreSQL 15432, файлы `.local-test/`; исходная пользовательская база не использовалась. В интерфейсе стенда находятся специально созданные учебные записи. PostgreSQL 17 использован из установленного окружения; запуск контейнеров Docker и Kubernetes в этой проверке не выполнялся, Docker Engine был выключен.

## Ограничения на момент первого этапа

**Обновление 6 октября 2026:** перечисленные ниже пункты закрыты в коде. Решения, актуальные проверки и границы проверки окружения приведены в [новом отчёте](HARDENING.md). Список ниже сохранён как история аудита.

1. GET-методы сервисов пока открыты: чтение пользователей и расписания не требует JWT. Перед внешним размещением нужны правила доступа к чтению, минимальные DTO пользователей и отдельная аутентификация межсервисных запросов. Защита мутаций не заменяет эти меры.
2. В исходной конфигурации остаются демонстрационные аккаунты, пароль БД и резервный JWT-секрет. Нужны внешняя конфигурация секретов, отключение учебной инициализации и ограничение сетевой доступности сервисов.
3. Физическое удаление аудитории или пользователя не согласуется с Booking Service: возможны записи со ссылкой на удалённый ресурс. Для рабочей системы нужно согласовать запрет удаления или мягкое удаление. Сейчас предпочтительно отключать аудиторию через isActive.
4. Одна БД с общими учётными данными сохраняет сильную зависимость микросервисов на уровне хранения. Она не заменялась, согласно требованию сохранить архитектуру. Нужны миграции схемы вместо автоматического ddl-auto для эксплуатации.
5. GraphQL в документации был заявлен, но реально не подключён: есть файл схемы, нет runtime и resolver-обработчиков. Notification Service отсутствует. README уточнён; текст старой курсовой и DOCX автоматически не переписывались.
6. История отдаётся целиком без пагинации. Полная нагрузочная проверка, проверка нескольких развёрнутых реплик, отказоустойчивость и аудит зависимостей не выполнялись. Проверка конкурентного бронирования проведена на одном экземпляре сервиса с параллельными HTTP-запросами.
7. Устаревшие записи с уже пересекающимися интервалами не исправляются автоматически. Перед переносом в существующую базу их нужно проверить отдельно.
