# Закрытие ограничений — 6 октября 2026

## Реализованные изменения

| Ограничение первого аудита | Решение |
| --- | --- |
| Открытые GET и полные сущности пользователей | Авторизация всех прикладных API; административный доступ к списку пользователей; UserView без пароля; чужая бронь показывает только занятость; внутренние маршруты требуют X-Service-Token и недоступны через Gateway |
| Известные секреты и начальные пароли | Обязательные переменные окружения; генератор уникальной конфигурации; единственный bootstrap-admin только на пустой базе; нет резервного JWT-секрета; внутренние порты не публикуются |
| Удаление ломает историю | Пользователи и помещения архивируются; история и идентификаторы сохраняются; неактивный пользователь теряет доступ даже с ранее выданным JWT |
| Общая база и автоматическое изменение схемы | Четыре базы, четыре отдельные роли, запрет чужих подключений, Flyway и ddl-auto=validate |
| Неработающий GraphQL и отсутствующие уведомления | Runtime и resolver-обработчики в Gateway; та же авторизация через REST; ограничение глубины/сложности GraphQL; отдельный Notification Service; транзакционная очередь событий, повторная доставка и устранение дубликатов |
| История целиком, проверки только одной реплики | Серверные страницы и фильтры; проверка двух реплик и сбоев; обновление зависимостей и аудит; ограниченный нагрузочный прогон |
| Старые пересечения | Предварительный анализ и резервная копия; все участники конфликта получают NEEDS_REVIEW; исходные данные остаются в журнале; администратор переносит либо отменяет запись |

Избранное теперь хранится в Notification Service и одновременно служит подпиской на изменения расписания помещения. Уведомления доставляются внутри приложения. Внешняя почта и push не заявляются как реализованные каналы.

## Безопасный перенос старой базы

1. Остановите запись в старую систему и сделайте обычную резервную копию PostgreSQL. Не удаляйте старую базу или том.
2. Создайте пустые целевые базы `<prefix>_users`, `<prefix>_rooms`, `<prefix>_bookings`, `<prefix>_notifications`. Запустите новые сервисы один раз с `BOOTSTRAP_ADMIN_ENABLED=false`, чтобы Flyway применил миграции, затем остановите сервисы на время импорта.
3. Установите `PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD` для оператора миграции, имеющего доступ к исходной и целевым базам; `PGCLIENTENCODING=UTF8`. Пароли не передаются аргументами команд.
4. Выполните предварительный анализ (Python 3 и psql):

   ```sh
   python scripts/migrate-legacy.py --source audit_system --prefix audit --backup backups/preflight
   ```

   Каталог должен быть новым. Он содержит полный снимок `source.json` и отчёт `report.json`. Снимок содержит хеши паролей и персональные данные: храните его как резервную копию с ограниченным доступом. Не включайте его в репозиторий.
5. Отсутствующие ссылки на пользователей/помещения и некорректные вместимости блокируют импорт без записи в целевые базы. Исправьте источник осознанно и повторите анализ. При пересечениях сохраняются **все** участники конфликта, без произвольного выбора «правильной» брони.
6. Для применения задайте новый пароль выбранного существующего администратора в `MIGRATION_ADMIN_PASSWORD` (16–72 байта), затем:

   ```sh
   python scripts/migrate-legacy.py --source audit_system --prefix audit --backup backups/import --apply --admin-id 1
   ```

   `--admin-id` замените реальным ID администратора. Известные демонстрационные аккаунты и аккаунты с незахешированными паролями отключаются; выбранный администратор получает новый BCrypt-пароль. Остальные допустимые хеши сохраняются.
7. Каждая база импортируется собственной транзакцией. Между базами нет общей транзакции: при сбое повторите команду с новым каталогом резервной копии и неизменным источником. Контрольные суммы и записи о завершённых этапах позволяют продолжить; чужие или уже заполненные без отметки импорта базы не перезаписываются.
8. Запустите сервисы, войдите администратором, откройте «Бронирования → Нужна проверка». Выберите новое свободное время либо отмените запись. Исходные интервалы и статусы находятся в `legacy_import_audit.original_record`; исходная база и резервная копия сохраняются.

Для локального Windows psql можно указать `--psql "C:/Program Files/PostgreSQL/17/bin/psql.exe"`.

## Kubernetes

Секретов в манифестах нет. В выбранном namespace создайте `audit-secrets` из сгенерированного `.env`:

```sh
kubectl create secret generic audit-secrets --from-env-file=.env
kubectl apply -f k8s/
```

Перед этим соберите и загрузите образы `audit/<service>:1.0.0` и `audit/client:1.0.0` в доступный кластеру реестр; при необходимости измените имена образов. PostgreSQL использует новый PVC `postgres-isolated-pvc`; старый PVC автоматически не переносится. Все Service имеют тип ClusterIP. Для локального просмотра: `kubectl port-forward service/client 3000:80`. Внешний ingress/TLS зависит от целевого кластера и настраивается отдельно.

## Повторение проверок

Основные команды сборки находятся в README. Интеграционные сценарии **создают и архивируют учебные записи** и должны запускаться только на выделенном стенде.

Текущий локальный набор использует `.local-test/harden.env`, содержащий bootstrap-параметры, Gateway 8080, сервисы 8081–8084 и вторую реплику Booking Service на 18083. `hardening-api.mjs` создаёт пользователей и сохраняет тестовую сессию в `.local-test/harden-test-session.json`; последующие сценарии используют её. Для `resilience-api.mjs` остановите только Notification Service и запустите вторую реплику с той же booking-базой. Затем восстановите Notification Service и выполните `notification-recovery.mjs`. `legacy-review.mjs` дополнительно требует тестовый PostgreSQL на 15432 и базу harden_bookings. Не запускайте эти сценарии против рабочей системы.

Для повторного аудита Maven сформируйте `dependency:list -DincludeScope=runtime -DoutputFile=<absolute-path>/.local-test/deps-<service>.txt` для всех пяти сервисов, затем `node scripts/audit-maven.mjs`. Скрипт отправляет OSV только публичные координаты и версии библиотек; код и секреты не отправляются.

Для другого выделенного стенда основной API-сценарий принимает `TEST_BASE_URL` (например, `http://localhost:3000`) и `TEST_SECRETS_FILE` (файл bootstrap-конфигурации этого стенда). Старый вход `tests/api-smoke.mjs` перенаправлен на актуальную проверку.
